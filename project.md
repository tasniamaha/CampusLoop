# CampusLoop: Product Requirements

Smart campus resource sharing, lost & found, and study collaboration platform.

This file is the source of truth for **what** CampusLoop must do. It does not track implementation progress, and it does not describe how the code is organised. When a requirement here conflicts with the code, the requirement wins unless a decision in §12 says otherwise. When this file is silent, the answer is an open decision (§13). Do not invent it.

---

## 1. Purpose

Verified university students share underused academic resources, borrow equipment, report lost or found items, and form study groups. The platform puts more weight on reliable transaction handling, privacy-aware moderation and measurable matching quality than on basic CRUD.

## 2. Scope

**In scope (first release)**
- One or more participating campuses.
- Free resource borrowing and exchange.
- Access limited to verified students (university email).
- Moderation and administration.
- Web-based notifications and real-time chat.

**Out of scope (first release)**
- Payments of any kind.
- Shipping or delivery.
- Native mobile apps.
- Automatic proof of lost-item ownership. A human always verifies.
- Semantic embeddings or external AI services for matching. These are an optional later phase that needs explicit approval.

## 3. Roles and permissions

| Role | Can | Cannot |
|---|---|---|
| Student | Verify account; manage own resources; request loans; report lost/found items; claim items; join and create groups; chat; review completed loans | Act on another user's resources, requests, messages, reports or claims |
| Moderator | Review suspicious listings, reports and claims; handle disputes; view non-public claim evidence needed for a case | Manage roles or platform settings |
| Administrator | Manage users, roles, categories, platform settings; view audit logs and analytics; export CSV | Bypass audit logging |

Rules:
- Every state-changing action is authorised on the server against the authenticated user. Client-supplied user IDs or ownership fields are never trusted.
- Unverified accounts may sign in, but they cannot create listings, request loans, file claims or join groups.

## 4. Modules and functional requirements

### 4.1 Authentication and profiles
- Register with a university email. The email is unique, compared case-insensitively in canonical form.
- Email ownership is verified with an expiring, single-use token.
- JWT access tokens plus refresh tokens with **rotation**. A refresh token is invalidated on use and on logout.
- Passwords are stored with a modern adaptive hashing algorithm.
- Account recovery uses an expiring, single-use reset token. A successful reset invalidates existing sessions.
- Profile settings include visibility controls over personal fields.
- Login, verification and reset endpoints are rate-limited.

### 4.2 Resource marketplace
- An owner creates, edits and soft-deletes a listing: title, description, category, condition, campus, images, borrowing rules.
- Categories are managed by administrators.
- Image uploads: content type is checked from file bytes (not the extension), size is limited, file keys are generated by the server, and storage permissions are safe.
- Search and filters (text, category, campus, availability), with paginated results.
- Users can favorite listings.
- Availability is derived from the loan state (§5.1), never set by hand from the client.

### 4.3 Borrowing and returns
See the workflow in §5.1 and the invariants in §6.
- Borrower submits a request. The owner approves or rejects it.
- Approval reserves the resource.
- Pickup and return are verified with QR codes.
- Due dates, plus reminders before and after the due date.
- Cancellation and expiry release the reservation.
- Either party can flag a dispute, which escalates to a moderator.
- Every transition is recorded as an immutable loan event.

### 4.4 Lost and found
See the workflow in §5.2.
- Structured lost and found reports: type, category, attributes (color, brand, and so on), campus, location, time window, description.
- The server generates match candidates for a report (§7).
- A user requests a claim on a found item and submits non-public proof.
- The finder or a moderator validates the proof.
- Public listings show limited fields only. Claim evidence is never visible to other users.

### 4.5 Study groups
- Create a group with course code, topic, campus, schedule and participant limit.
- Discover groups by course, topic and campus.
- Join requests are approved or rejected by the group owner.
- Group roles: owner and member.
- The participant limit is enforced on the server, including under concurrent joins.
- Recommendations combine shared course/topic, availability windows and declared campus preference.

### 4.6 Chat and notifications
- Real-time messaging over Socket.IO. The sender must be a participant in the conversation, and the connection is authenticated at handshake.
- Notifications are persisted, have unread state, and are actionable: request alerts, approvals, reminders, claim updates.
- Reminders and notification delivery run as background jobs (Redis + BullMQ), with retry and failure handling. A rolled-back transaction must not produce a notification.

### 4.7 Trust and reviews
- Reviews may only be left for a **completed** loan, by its participants, at most once per participant per loan.
- Reputation is computed only from verified completed transactions. It is transparent (the user can see how it was derived) and bounded.
- Anti-abuse: reviews can be reported and moderated. No self-review.

### 4.8 Admin and reporting
- Moderation queues for reported listings, reviews, claims and disputes.
- User and role management.
- Audit log of security-relevant and moderation actions.
- Operational dashboard and analytics.
- CSV export, restricted to authorised roles.

## 5. Core workflows

### 5.1 Borrowing lifecycle

```
pending ──approve──▶ approved ──pickup QR──▶ active ──return QR──▶ returned
   │                    │
   ├─reject──▶ rejected │
   ├─cancel──▶ cancelled◀┤ cancel
   └─expire──▶ expired ◀─┘ expire
```

- **Occupying states:** `approved` and `active`. Only these reserve the resource.
- **Terminal states:** `returned`, `rejected`, `cancelled`, `expired`. A terminal state never transitions again.
- Who can trigger each transition:
  - Approve or reject: the owner.
  - Cancel: the borrower, or the owner before pickup.
  - Pickup and return: QR-verified handover between both participants.
  - Expire: the system.
- A dispute is a flag on a loan, not a lifecycle state. It does not change availability by itself.
- Every transition writes a loan event in the same database transaction as the status change.

### 5.2 Lost and found

Report filed with non-sensitive attributes → server generates candidates → user requests a claim with private proof → finder or moderator validates → private handover is coordinated → case closes.

Identifying details and proof images are never published to all users.

### 5.3 Study group membership

Join request (`pending`) → owner approves (`active`) or rejects (`rejected`). Approval fails if the group is full.

## 6. Business invariants

These must hold under concurrent requests. They are enforced in the database layer (transactions, row locks, conditional updates, constraints), not only in application checks or the UI.

- **INV-1:** A single-unit resource never has more than one loan in an occupying state.
- **INV-2:** Loan events are append-only. They are never updated or deleted.
- **INV-3:** A QR handover token is unpredictable, expires, is single-use, and is bound to one loan, one action (pickup or return) and its authorised participants. Only a hash of the token is stored. A replayed or duplicate handover is rejected.
- **INV-4:** A study group never exceeds its participant limit.
- **INV-5:** At most one review per participant per completed loan.
- **INV-6:** Users can read and modify only what they own or are authorised to act on (no IDOR).
- **INV-7:** All timestamps are stored in UTC.

## 7. Lost-and-found matching

**Filters before ranking:** same campus, and compatible item type (a lost report matches found reports, and vice versa).

**Baseline score (weights tunable on a labelled set):**

| Signal | Weight |
|---|---|
| Text similarity | 35% |
| Item category | 25% |
| Color and attributes | 15% |
| Location proximity | 15% |
| Time window | 10% |

- Each candidate is returned with an explanation of which signals contributed and by how much.
- **Evaluation:** Precision@5, Recall@5, Mean Reciprocal Rank and response latency, measured on a documented labelled test set and compared against a keyword-only baseline.
- No claim of improvement without measured results.

## 8. Security and privacy

- Validated DTOs on all input. RBAC plus per-resource access checks on every endpoint.
- Rate limits on authentication, email-sending and write-heavy endpoints.
- Audit logging for authentication events, role changes, moderation actions and dispute resolution.
- No secrets in source control. Configuration comes from environment variables.
- Never return password hashes, token hashes or internal error details to clients.
- Show limited fields on public lost-and-found listings. Claim evidence is visible only to the claimant, the finder and moderators.
- Least privilege, profile visibility controls, and a data retention policy (§13).

## 9. Data model

**Core entities:** users, user profiles, verification tokens, roles, resources, resource categories, resource images, resource favorites, borrow requests/loans, loan events, lost/found reports, item matches, item claims, study groups, study group members, conversations, conversation members, messages, notifications, reviews, reports, audit logs.

| Relationship | Rule |
|---|---|
| User → Resource | One-to-many. A resource has exactly one owner. |
| Resource → Borrow request | One-to-many. A request belongs to one borrower. |
| Borrow request → Loan | At most one active or completed loan after approval. |
| Lost/found report ↔ Report | Many-to-many through matches, with score and explanation. |
| Study group ↔ User | Many-to-many through membership. |
| Conversation → Message | One-to-many. The sender must be a participant. |
| Completed loan → Review | Optional, at most one per participant. |

**Constraints:**
- Unique canonical university email.
- Indexes on resource status, category and campus.
- Foreign keys throughout.
- Soft deletion for user-generated content that other records reference.
- UTC timestamps.
- Schema changes only through migrations.

## 11. Acceptance criteria

| Area | Criterion |
|---|---|
| Core workflow | A student can list, borrow, hand over and return an item through a complete, audited lifecycle. |
| Data integrity | Simultaneous approvals never create two occupying loans for a single-unit resource (tested against a real database). |
| Security | Unauthorised users cannot modify others' resources, requests, messages, reports or claims (negative-path tests). |
| Matching | Documented test set; Precision@5, Recall@5 and MRR reported against the keyword baseline. |
| Performance | p50/p95 latency of major endpoints measured under documented simulated load. |
| Usability | Task-based testing with students; completion rates and observed issues summarised. |

## 12. Decided

- **Frontend:** Next.js (App Router), React, TypeScript, Tailwind CSS.
- **Backend:** NestJS, REST + Swagger/OpenAPI, class-validator DTOs, Socket.IO for chat.
- **Database:** MySQL 8 with TypeORM (chosen over Prisma). Migrations only, no schema sync.
- **Async processing:** Redis + BullMQ.
- **Monorepo:** NestJS owns all business rules and database writes. Next.js never writes to the database directly, and secrets stay server-side.
- **Expiry windows:** A `pending` request expires when its due date passes. An `approved` loan expires when its due date passes, or if it isn't picked up within `BORROW_PICKUP_WINDOW_HOURS` (default 48) of approval, whichever comes first. A background check runs every 5 minutes, so expiry can be up to about 5 minutes late.
- **Reputation:** a Bayesian average, `(priorWeight × priorMean + ratingSum) / (priorWeight + reviewerCount)`, with prior weight 5 and prior mean 3.5, rounded to 2 decimal places.
  - **One vote per reviewer:** `ratingSum` adds one value per distinct reviewer: the average of all that reviewer's ratings of this user. `reviewerCount` is the number of distinct reviewers.
  - **Which reviews count:** reviews of this user that are not hidden, that are either revealed or past their review window, and that are on a loan in status `returned` which has a `handed_over` event.
  - **Bounds:** ratings range from 0.5 to 5, so the score stays within 0.5–5 with no separate clamp. A user with no reviews scores 3.5.

### Known limitations

- A crash between a transaction commit and the notification enqueue loses that notification. Planned fix: a transactional outbox using the notifications table.
- Found-item photo files stay on disk when a report row is cascade-deleted, until a retention policy exists.
- Lost-and-found matches are computed per request, not stored in `item_matches`.
- `updatedAt` is stored at whole-second precision on updates, so it can be earlier than `createdAt`. This is a bug, to be fixed.

## 13. Open decisions

Ask before implementing anything that depends on these. Record the answer in §12 once it is decided.

1. **Multi-unit resources:** are resources with quantity > 1 supported, and how does INV-1 generalise?
2. **Loan rules:** maximum loan duration, and whether loans can be extended.
3. **Disputes:** resolution outcomes, and their effect on reputation.
4. **Data retention:** periods for chat messages, claim evidence, audit logs and deleted accounts; and how account deletion coexists with immutable loan history (for example, anonymisation).
5. **Image storage:** object storage or Cloudinary in production.
6. **Frontend extras:** whether shadcn/ui and Playwright end-to-end tests are adopted.
7. **Repeated join requests:** after the owner rejects a join request, may the student request again, and if so how often (no limit, a cooldown, a maximum number of attempts, or never)? Today a rejected student can re-request with no limit.
8. **Archiving and pending requests:** what happens to `pending` join requests when the owner archives a group (left pending, rejected automatically, or withdrawn), and are the requesters notified? Today they stay `pending`.
9. **Campus normalisation:** users and resources store the campus as typed, while study groups normalise it (for example `IUT` and "Islamic University of Technology"). Should every module normalise campus names the same way, and how are existing rows migrated?
10. **Deactivated users' listings and loans:** what happens to a deactivated user's listings, reports and groups, and to loans in progress (for example, a borrower with a `pending` or `approved` loan on a deactivated owner's resource)? Today deactivation only blocks access, and all content stays as it is.
